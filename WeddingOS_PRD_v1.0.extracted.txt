0029: 1. EXECUTIVE SUMMARY & VISION
0030: 1.1 The Problem We Are Solving
0031: India's wedding industry is worth ₹2,00,000 Crore annually — the second-largest wedding market in the world. Yet, every single wedding is planned through WhatsApp groups, Excel sheets, phone calls, and local referrals. This results in:
0032: Vendor no-shows causing wedding-day disasters with zero accountability
0033: No price transparency — couples overpay by 30–40% due to information asymmetry
0034: Zero coordination between 15–20 vendors working the same event
0035: Advance payments lost with no escrow protection or dispute resolution
0036: Planning takes 200+ hours spread over 12–18 months with no central system
0037: Vendor quality is unpredictable — no verified portfolio or ratings system
0038: 1.2 Our Solution — The Wedding OS

0040: We are building the infrastructure layer of India's wedding industry — where every wedding runs on our platform. Think of it as:

0042: Zoho CRM — for vendor lead and booking management

0194: 3. DATABASE DESIGN
0195: 3.1 Database Philosophy
0196: Principle: Read-optimized design with write separation. 80% of traffic is reads. Use denormalization where performance demands it. Every critical table has soft deletes, audit columns, and proper indexing.
0197: 3.2 Core Entity Relationship Overview
0198: Primary entities and their relationships:
0199: USERS → has one PROFILE → has many BOOKINGS → has many PAYMENTS
0200: VENDORS → has one VENDOR_PROFILE → has many PACKAGES → has many BOOKINGS
0201: BOOKINGS → belongs to USER + VENDOR → has many MILESTONES → has many TASKS
0202: EVENTS → has many VENDORS → has many TASKS → has one TIMELINE
0203: PAYMENTS → belongs to BOOKING → has ESCROW_HOLD → releases to VENDOR_WALLET

0206: CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  phone VARCHAR(15) UNIQUE NOT NULL,
  email VARCHAR(255) UNIQUE,
  email_verified BOOLEAN DEFAULT FALSE,
  phone_verified BOOLEAN DEFAULT FALSE,
  password_hash VARCHAR(255),
  role ENUM('customer','vendor','admin','coordinator') NOT NULL,
  status ENUM('active','suspended','deleted') DEFAULT 'active',
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  deleted_at TIMESTAMPTZ
);

CREATE TABLE user_profiles (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  full_name VARCHAR(255) NOT NULL,
  avatar_url TEXT,
  city VARCHAR(100),
  state VARCHAR(100),
  language_preference VARCHAR(20) DEFAULT 'en',
  notification_preferences JSONB DEFAULT '{}',
  metadata JSONB DEFAULT '{}'
);

CREATE TABLE refresh_tokens (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  token_hash VARCHAR(255) UNIQUE NOT NULL,
  device_id VARCHAR(255),
  expires_at TIMESTAMPTZ NOT NULL,
  revoked_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

  total_bookings INTEGER DEFAULT 0,
  is_featured BOOLEAN DEFAULT FALSE,
  subscription_tier ENUM('free','premium','enterprise') DEFAULT 'free',

0212: CREATE TABLE payments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

0470: 5. SECURITY ARCHITECTURE
0471: SECURITY PHILOSOPHY: Zero-trust architecture. Every request is authenticated, every action is authorized, every piece of data is encrypted, every input is validated. Security is not a feature — it is the foundation.
0472: 5.1 Authentication & Authorization
0473: 5.1.1 JWT Token Strategy
0474: Access Token: Short-lived (15 minutes), RS256 signed (asymmetric key)
0475: Refresh Token: Long-lived (30 days), stored as httpOnly cookie + DB hash
0476: Token Rotation: Each refresh generates new access + refresh pair
0477: Token Revocation: Blacklist in Redis with TTL matching token expiry
0478: Device binding: Refresh tokens bound to device_id fingerprint
0479: 5.1.2 Role-Based Access Control (RBAC)
0480: Role
0481: Permissions
0482: Scope
0483: customer
0484: Read vendors, create bookings, manage own events
0485: Own resources only
0486: vendor
0487: Manage own profile, view/manage own bookings, access Vendor OS
0488: Own business only
0489: coordinator
0490: View all bookings, manage tasks, coordinate events
0491: Assigned events only
0492: admin
0493: Full system access, approve vendors, manage disputes
0494: System-wide
0495: super_admin
0496: All admin + billing, user deletion, system config
0497: Unrestricted
0498: 5.1.3 OTP Security
0499: OTP: 6-digit, cryptographically random, 10-minute expiry
0500: Rate limiting: 3 OTP requests per phone per 10 minutes
0501: Lockout: After 5 failed attempts, 30-minute lockout
0502: OTP never stored in plaintext — SHA-256 hash only
0503: SMS delivery via Twilio/MSG91 with delivery confirmation
0504: 5.2 Data Security
0505: 5.2.1 Encryption

const crypto = require('crypto');

function verifyWebhookSignature(body, signature, secret) {
  const expectedSig = crypto
    .createHmac('sha256', secret)
    .update(JSON.stringify(body))
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expectedSig), Buffer.from(signature)
  );
}

1143: TTL-based: All caches have max TTL as safety net
1144: Selective: Only invalidate the specific vendor/booking, not entire namespace
1145: 11.2 Database Performance
1146: 11.2.1 Connection Pooling
1147: PgBouncer: Connection pooler in front of PostgreSQL (transaction mode)
1148: Pool size: min 10, max 100 connections per service
1149: Idle timeout: 30 minutes
1150: Max connection age: 1 hour (prevents connection leaks)
1151: 11.2.2 Query Optimization Rules
1152: All queries use indexed columns in WHERE clauses
1153: N+1 query prevention: Use JOINs or DataLoader for batch fetching
1154: Large result sets: Always cursor-paginate, never fetch >1000 rows
1155: Read replicas: All GET endpoints read from replica; writes go to primary
1156: EXPLAIN ANALYZE: Required in PR review for any new query

1665: 18.3 Edge Cases to Handle
1666: Vendor Side
1667: Vendor account suspended mid-event → Coordinator takes over, emergency vendor replacement
1668: Vendor changes price after quote accepted → Not allowed, original quote locked
1669: Vendor requests event date change → Requires customer approval via platform
1670: Vendor uploads fake portfolio → Report system + admin review + suspension policy
1671: Customer Side
1672: Customer books same vendor twice for same event → Warn and prevent duplicate
1673: Customer changes guest count after booking → Notify vendor, re-quote if significant (>20%)
1674: Customer disputes after review window closed → Case-by-case, max 30 days post-event
1675: Customer no-shows at their own event → Platform still releases vendor payment after 7 days
1676: Payment Edge Cases
1677: Payment gateway down → Queue payment attempts, retry every 5 min for 1 hour, alert customer
1678: Partial payment received → Do not confirm booking; hold in 'partial payment' state
1679: Currency mismatch → All amounts stored in INR paise; convert only at display layer
1680: Refund to original payment method → Always refund to source (card/UPI/wallet)

1684: TDS on vendor payouts: Deduct 1% TDS if cumulative payment >₹30,000/year per vendor
1685: DPDP Act 2023: Data localization (store Indian user data in Indian data centers — AWS ap-south-1)
1686: Consumer Protection Act: Refund SLA of 5–7 business days
